# Конверсии и Postbacks

## Каталог статусов кампании

В разделе **Conversions** настроек кампании находится общий каталог статусов. У каждой строки есть:

- неизменяемое внутреннее имя, используемое YellowTDS;
- входящие aliases через запятую.

Сопоставление регистронезависимое. Имя или alias может принадлежать только одному статусу. Lead, Purchase, Reject и Trash нельзя переименовать или удалить, но их aliases можно менять. Кастомные статусы, например Reg, Dep или Install, добавляются без фиксированного лимита.

Перед удалением кастомного статуса интерфейс показывает его текущие и исторические использования. Снимки кликов, история конверсий и сохранённые отчёты не удаляются; новое входящее имя и его aliases перестают распознаваться.

## Входящий postback

Запрос к `api/postback.php` принимает:

- `clickid` — обязательный идентификатор клика;
- `status` — обязательное внутреннее имя или alias;
- `payout` — необязательное неотрицательное число, по умолчанию `0`;
- `currency` — необязательный трёхбуквенный код, по умолчанию `USD`;
- `tid` — необязательный идентификатор транзакции; это имя параметра по умолчанию, его можно изменить или дополнить в **Conversions → Transaction ID parameters**;
- `pbkey` — требуется только при включённой **Key protection** кампании.

Пример:

```text
/api/postback.php?clickid={sub1}&status={status}&payout={payout}&currency=USD&tid={transaction_id}&pbkey=secret
```

В **Transaction ID parameters** можно указать до 32 имён через запятую, например `tid, order_id, transaction_id`. Имя состоит из ASCII-букв, цифр, `_` или `-`, начинается с буквы или `_` и не может подменять служебные поля `clickid`, `status`, `payout`, `currency` и `pbkey`. У каждого имени собственное пространство дедупликации, поэтому `order_id=123` и `transaction_id=123` могут быть разными транзакциями из разных партнёрских программ.

В одном postback следует передавать не более одного непустого настроенного Transaction ID parameter. Пустые значения игнорируются; несколько непустых имён, массивы, управляющие символы и один параметр, одновременно переданный в query string и POST body, отклоняются. GET и form POST обрабатываются явно, cookies никогда не используются как параметры postback.

Первый принятый статус становится initial-конверсией clickid. Последующие смены статуса сохраняются в истории, но не увеличивают базовую метрику **Conversions**. В `clicks.status` хранится последний принятый статус, в `clicks.payout` — накопленный revenue. Исходный входящий status сохраняется в истории для диагностики.

Неизвестный статус отклоняется и записывается в warning log. Если включена **Key protection**, любой отклонённый postback возвращается как обычный `404 Not Found`, кроме Debug Mode. Без Key protection YellowTDS всегда возвращает фактический JSON-результат.

## Дедупликация и платные повторы

При включённой дедупликации Transaction ID можно использовать только один раз внутри того настроенного параметра, через который он пришёл. Для платного повтора текущего статуса нужен новый ID в этом пространстве; исправление status или payout повторным ID не поддерживается. Повтор текущего статуса без payout отклоняется всегда.

При выключенной дедупликации настройка **Paid repeat without transaction ID** определяет поведение платного повтора текущего статуса:

- **Reject duplicate** — отклонить; это значение по умолчанию.
- **Accept as upsell** — добавить ещё одну строку истории и её payout.

## Другие источники конверсий

Все источники используют один resolver и одну историю:

- **Successful proxied form** может создавать zero-payout статус; по умолчанию выбран Lead.
- **Website status tracking** добавляет на маршрутизируемые страницы функцию `ytdsConversion(status)`. Она использует текущий clickid, принимает внутреннее имя или alias и не принимает payout.

```javascript
ytdsConversion('Reg').then(console.log).catch(console.error);
```

## Исходящие S2S postbacks

В разделе **Postbacks** у каждого правила S2S задаются URL, метод `GET` или `POST` и два независимых поля с поиском: **Conversion statuses** и **Events**. Выбранные значения отображаются как chips; их можно найти вводом, добавить или удалить без изменения остальных настроек правила.

- **Conversion statuses** содержит внутренние статусы из каталога Conversions. При конверсии в URL доступен макрос `{status}` с нормализованным внутренним именем статуса.
- **Events** содержит только включённые browser events: настроенные пороги `scroll_*`, `stay_*` и разрешённые custom events. Performance/RUM-метрики не являются S2S events и в этом поле не показываются.

Выборы объединяются по **OR**: правило запускается, если наступил любой выбранный conversion status **или** любой выбранный event. Если оба поля пусты, правило ничего не запускает. Каждая принятая строка истории, включая принятый платный повтор, может запустить выбранный conversion status.

Для browser event отправка возможна только один раз на комбинацию `clickid + step + event`. Повторные пересечения scroll-порога, повторное достижение visible-time порога или повторный вызов custom event не создают новую S2S-отправку для той же комбинации.

### Макросы

Для S2S, запущенного конверсией, доступны `{clickid}`, `{userid}`, `{domain}`, `{status}` и макросы параметров клика `c.*`, если они настроены в URL. `{status}` заменяется нормализованным внутренним именем статуса.

Для S2S, запущенного browser event, доступны `{clickid}`, `{userid}`, `{domain}`, `c.*`, а также `{event}`, `{event_value}`, `{step_index}`, `{variant}` и `{trigger_type}`. `{status}` относится только к конверсионной отправке.

### Доставка и доверие к событиям

S2S, запущенный browser event, отправляется в режиме fire-and-forget: YellowTDS записывает HTTP-запрос в write-only socket и не ждёт HTTP-ответ партнёрки. Для таких отправок нет очереди, повторов или гарантии доставки; недоступный сервер, ошибка сети или ответ партнёрки после записи не будут автоматически обработаны повторно. Conversion-status S2S остаётся обычной подтверждаемой отправкой. Используйте event-triggered S2S для best-effort уведомлений, а не как единственное подтверждение финансовой конверсии.

Browser events приходят со страницы посетителя и считаются недоверенными сигналами вовлечённости. Их нельзя использовать как защищённое доказательство оплаты, антифрода или серверного статуса; включайте в S2S только там, где такая best-effort семантика приемлема.
